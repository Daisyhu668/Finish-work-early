# 银承开票｜近一周贴现及资金来源核查

先读取 [共用工作规则](../_shared/WORKFLOW.md)。本技能为银承前置准备的资金来源子模块，独立于发票登记、BI关联与贴现专门授信。用户说“企业一周内有贴现，写说明”等同义表达时即触发整套流程，不仅返回文字。除用户明确仅需文字外，默认交付Word、银行流水重命名副本、合并流水及压缩包。

## 执行顺序
1. 识别企业完整法定名称、征信查询实际日期、开票日期、客户确认的资金来源。按北京时间确定“今天”；用户确认今日查询征信且近一周存在贴现时，可以按其业务陈述写入。没有确认不得假称已查询征信。近一周以实际征信查询口径为准，默认查询日前7日至查询当日（含），不得机械遗漏边界日或声称流水覆盖未提供日期。
2. 打开所有流水逐页读取：先提取PDF文本，再核对页面图像；扫描件或文字错位必须看图，必要时OCR辅助，不能按文件名推断。核对户名、开户银行、查询期间、交易日期、摘要、借贷方向、金额、交易流水号、收款方全称和余额。多客户、多账号分开，不混用。
3. 按银行、日期识别真正贴现放款及对应利息。直接净额入账不能再次扣息；本金与利息分别入账/扣款时，本金减对应贴现利息得净额。普通转入、账户互转及手续费不能计入贴现。按交易唯一标识及账户核重，重复PDF不得重复计算。
4. 核对每笔贴现后资金路径，按收款企业归集金额，保留日期及完整户名。优先追踪同日及随后对外支出，不机械把全部支出归入贴现。仅摘要或合同支持货款用途时才写货款；普通“转款”写支付、对外结算。转回本行、同名划转、存单入金、关联方循环、余额未对平、异常留存或缺少后续流水，标记待核查，不能直接认定无关联。
5. 使用 Decimal 精确到分计算笔数、实际到账、贴现利息、对外支付、手续费及期末余额。执行“期初余额+全部入账−全部出账=期末余额”；核对银行页尾汇总；差异非零先复核，无法解释则暂停生成无保留结论。明确净额/本金口径。对外支付略高于贴现净额时检查期初余额，不擅自调整金额。
6. 根据资金来源证据状态选择结尾：已核实本次存单入金（verified）、仅客户说明（customer_confirmed）、拟使用自有资金但未核实（pending）、存在异常（exception）。既有贴现流出不等于本次存单已证明为自有资金；无入金证据不得称已经核实。用户确认的事实与流水能证明的事实分开。
7. 按模板生成一段可直接复制的正文，不加星号、Markdown或条目。Word独立正式标题、正文一段。输出每家银行一份原PDF副本和按银行顺序合并的PDF；不删页、不截图替代、不修改银行原始内容、印章、日期或交易数据。合并版和独立版是两种上传方式，提示避免重复上传。
8. 运行脚本、核查Word排版、PDF页数与源页渲染一致性；输出实际文件及简要核验提示。将本次有效交付文件打包，内部底稿及客户隐私不进入通用技能或公共仓库。无关键材料时先交可核部分及明确缺口，不伪造结论。

## 固定说明结构
客户经理于YYYY年M月D日查询企业征信，发现【企业全称】近一周内有贴现业务。经核查客户提供的银行账户流水，具体情况如下：于【日期】在【银行】办理贴现业务【笔数】笔，贴现资金实际到账【金额】元，后续向【收款方全称】支付【金额】元；【其他银行同样列示】。上述贴现业务合计【笔数】笔，实际取得资金【金额】元。【经证据支持的资金去向归纳】。【按证据状态选择资金来源结论】。特此说明。

## 文件命名（企业名称在前）
- 企业全称贴现情况说明.docx
- 企业全称贴现流水-银行名称.pdf（每家银行独立保留；多账号时添加必要区分标签）
- 企业全称贴现流水-合并.pdf（多份流水合并，页序按正文银行顺序）
- 企业全称贴现材料.zip（本次交付包）
单银行可仅保留原命名副本及Word，不重复上传相同PDF。简称仅用于沟通，不用于归档。

## 工具与验证
读取 `references/input-schema.md`，将已人工/Agent复核的交易行整理为本地JSON，然后运行：
`python scripts/build_package.py /path/to/reviewed.json /path/to/empty-output`
依赖 python-docx、pypdf；安装参考 requirements.txt。脚本是计算和归档工具，不是通用OCR，也不自动判断真实贸易背景。生成前必须完成第1至6步。测试：`python -m unittest discover -s tests -v`。

## 接入现有工作流
“近期贴现、近一周有贴现、贴现说明、贴现流水、开票资金来源”触发此技能；发票相关任务仍转原发票双阶段技能；同一请求涉及两者时按阶段组合。不得擅自修改OA、征信或信贷系统。公共仓库禁止真实客户流水、账号、案例数据及已填成品。
